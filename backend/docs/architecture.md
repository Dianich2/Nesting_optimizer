# Nesting Optimizer Backend Architecture

## 1. Purpose

Данный документ описывает архитектуру backend-приложения **Nesting Optimizer**, основные принципы проектирования системы, организацию исходного кода, взаимодействие компонентов и правила дальнейшего развития проекта.

Документ предназначен для разработчиков, участвующих в разработке и сопровождении проекта. Его цель - предоставить целостное представление об архитектуре системы, не углубляясь в детали реализации отдельных компонентов.

Подробное обоснование отдельных архитектурных решений приводится в документах **Architecture Decision Records (ADR)**.

---

## 2. High-Level Overview

Nesting Optimizer представляет собой backend-приложение, построенное по принципам слоистой архитектуры.

Основной поток обработки запроса проходит через несколько независимых уровней, каждый из которых отвечает только за собственную область ответственности.

Высокоуровневая схема взаимодействия компонентов выглядит следующим образом:
                    Frontend
                        │
                  HTTP / JSON
                        │
                        ▼
              Fiber HTTP Server
                        │
                        ▼
                  HTTP Handler
                        │
                        ▼
                    Use Case
                        │
           ┌────────────┴────────────┐
           ▼                         ▼
   Domain Services             Repository
                                         │
                                         ▼
                            PostgreSQL + PostGIS

Основные принципы организации системы:
- frontend отвечает за взаимодействие пользователя с системой и визуализацию данных;
- HTTP-слой отвечает только за приём запросов и формирование ответов;
- бизнес-логика приложения сосредоточена в уровне Use Case;
- доступ к базе данных осуществляется исключительно через Repository;
- доменные модели и доменные сервисы не зависят от инфраструктурных компонентов;
- backend является единственным источником истины для всех бизнес-решений;
- геометрическая обработка распределяется между Go и PostGIS в соответствии с зонами их ответственности.

## 3. Architectural Principles
Архитектура проекта основана на нескольких фундаментальных принципах, определяющих организацию исходного кода, взаимодействие компонентов системы и правила её дальнейшего развития.

Данные принципы являются руководящими (Guiding Principles) для дальнейшего развития проекта.

Каждый новый модуль проекта должен соответствовать данным принципам. При возникновении необходимости изменить один из них принимается отдельное архитектурное решение, которое фиксируется в документах Architecture Decision Records (ADR).

### 3.1 Separation of Responsibilities

Каждый компонент системы отвечает только за собственную область ответственности.

HTTP-слой занимается исключительно взаимодействием с клиентом.

Use Case координирует выполнение бизнес-сценариев.

Repository отвечает за работу с базой данных.

Domain содержит бизнес-модель предметной области и не зависит от инфраструктурных компонентов.

Такое разделение уменьшает связанность компонентов системы и облегчает сопровождение проекта.

Подробнее см. ADR-0001.

### 3.2 Explicit SQL

Проект использует явные SQL-запросы вместо ORM.

Такой подход обеспечивает полный контроль над взаимодействием с PostgreSQL и позволяет эффективно использовать возможности PostGIS без дополнительных ограничений.

Подробнее см. ADR-0002.

### 3.3 Infrastructure as Code

Инфраструктура проекта описывается декларативно с помощью Docker Compose, Makefile и миграций Goose.

Это позволяет воспроизводить одинаковое окружение разработки на любом компьютере без ручной настройки.

Подробнее см. ADR-0003 и ADR-0005.

### 3.4 Configuration Outside the Code

Конфигурация приложения полностью отделена от исходного кода.

Все параметры запуска загружаются из переменных окружения через централизованный механизм конфигурации.

Это позволяет использовать один и тот же исполняемый файл в различных окружениях без изменения исходного кода.

Подробнее см. ADR-0004.

### 3.5 Server-side Business Decisions

Frontend отвечает за взаимодействие пользователя с системой и выполнение временных вычислений, необходимых для обеспечения плавной работы интерфейса.

Окончательные бизнес-решения принимаются исключительно backend-приложением.

Пространственные операции распределяются между Go и PostGIS в соответствии с их зонами ответственности, а backend остаётся единственным источником истины для всех сохраняемых геометрических данных.

Подробнее см. ADR-0006.

## 4. System Components

Архитектура Nesting Optimizer состоит из нескольких крупных подсистем, каждая из которых выполняет собственную роль и взаимодействует с остальными компонентами через чётко определённые интерфейсы.

Такое разделение позволяет независимо развивать отдельные части системы, не нарушая общую архитектуру проекта.

### 4.1 Frontend

Frontend представляет собой пользовательский интерфейс системы.

Он отвечает за:
- визуализацию проектов;
- отображение поверхностей и шаблонов;
- взаимодействие пользователя с системой;
- выполнение временных клиентских вычислений, необходимых для плавной работы интерфейса.

Frontend не содержит бизнес-логики приложения и не принимает окончательных решений, связанных с корректностью геометрических операций.

Окончательная проверка всех действий выполняется backend-приложением.

### 4.2 Backend

Backend является центральной частью системы.

Он координирует выполнение всех бизнес-сценариев приложения, обеспечивает взаимодействие между компонентами системы, принимает окончательные решения о корректности выполняемых операций и управляет доступом к данным.

Именно backend является единственным источником истины для бизнес-логики приложения.

### 4.3 Database

В качестве основного хранилища данных используется PostgreSQL с расширением PostGIS.

База данных отвечает за долговременное хранение информации о пользователях, проектах, поверхностях, шаблонах, размещениях и других сущностях предметной области.

Кроме хранения данных PostGIS используется для выполнения стандартных пространственных операций и геометрических запросов.

### 4.4 Geometry Engine

Геометрическая подсистема объединяет возможности Go и PostGIS для обработки пространственных данных.

Стандартные геометрические операции выполняются средствами PostGIS.

Сложные алгоритмы автоматического раскроя, оптимизации размещения и координации вычислений реализуются на стороне backend с использованием Go.

Такое распределение ответственности позволяет эффективно использовать сильные стороны каждой технологии и избегать дублирования функциональности.

                 HTTP / JSON
                       │
        ┌──────────────▼───────────────┐
        │          Backend             │
        │                              │
        │  • HTTP Layer                │
        │  • Use Cases                 │
        │  • Domain                    │

## 5. Geometry Processing Architecture

Обработка геометрических данных является ключевой особенностью проекта Nesting Optimizer.

В отличие от большинства backend-приложений, система не ограничивается хранением данных, а выполняет большое количество пространственных вычислений, необходимых для проверки корректности размещения объектов и реализации алгоритмов автоматического раскроя.

Для достижения высокой производительности и сохранения чёткого разделения ответственности обработка геометрии распределяется между несколькими компонентами системы.

                    Geometry Processing
                 ┌──────────────────────┐
                 │      Frontend        │
                 │                      │
                 │ • Rendering          │
                 │ • Drag & Drop        │
                 │ • Preview            │
                 │ • Temporary UI Calc. │
                 └──────────┬───────────┘
                            │
                     HTTP / JSON
                            │
                            ▼
                 ┌──────────────────────┐
                 │     Backend (Go)     │
                 │                      │
                 │ • Business Logic     │
                 │ • Use Cases          │
                 │ • Nesting Algorithms │
                 │ • Validation         │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │ PostgreSQL + PostGIS │
                 │                      │
                 │ • Geometry Storage   │
                 │ • ST_Intersects()    │
                 │ • ST_Contains()      │
                 │ • ST_Area()          │
                 └──────────────────────┘

### 5.1 Frontend Responsibilities

Frontend отвечает исключительно за взаимодействие пользователя с системой.

Во время работы пользователь может перемещать объекты, изменять их положение, масштабировать рабочую область и выполнять другие действия, влияющие только на визуальное представление данных.

Для обеспечения плавности интерфейса frontend может выполнять временные вычисления, необходимые исключительно для отображения информации пользователю.

Результаты таких вычислений не используются для принятия окончательных бизнес-решений.

### 5.2 Backend Responsibilities

Backend координирует выполнение всех геометрических сценариев приложения.

Именно backend принимает окончательное решение о корректности размещения объектов, запускает алгоритмы автоматического раскроя, управляет взаимодействием с PostGIS и определяет дальнейшее поведение системы.

Backend является единственным источником истины для всех сохраняемых геометрических данных.

### 5.3 PostGIS Responsibilities

PostGIS используется как специализированный пространственный движок.

Он отвечает за хранение геометрических объектов и выполнение стандартных пространственных операций, предоставляемых PostgreSQL.

К числу таких операций относятся:
- проверка пересечений;
- вычисление площади;
- проверка принадлежности объектов;
- пространственные запросы;
- другие встроенные функции PostGIS.

Использование встроенных возможностей PostGIS позволяет избежать повторной реализации уже существующих алгоритмов средствами Go.

### 5.4 Geometry Workflow

Типичный сценарий обработки геометрической операции выглядит следующим образом:

1. Пользователь выполняет действие во frontend.
2. Frontend обновляет визуальное состояние интерфейса.
3. После завершения действия запрос отправляется в backend.
4. Backend выполняет бизнес-проверки.
5. При необходимости backend использует пространственные функции PostGIS.
6. Backend принимает окончательное решение.
7. Результат возвращается frontend и отображается пользователю.

### Design Principle

При проектировании геометрической подсистемы используется следующее правило:

> Каждая технология должна использоваться для решения тех задач, для которых она предназначена.

Frontend отвечает за пользовательский интерфейс.

Go отвечает за бизнес-логику и алгоритмы.

PostGIS отвечает за пространственные операции.

Такой подход позволяет минимизировать дублирование функциональности и эффективно использовать сильные стороны каждого компонента системы.

## 6. Layers of the Application

Backend-приложение построено на основе слоистой архитектуры.

Каждый слой отвечает за выполнение строго определённого набора задач и взаимодействует только с теми компонентами, которые определены архитектурой проекта.

Такой подход уменьшает связанность компонентов, упрощает тестирование, облегчает сопровождение системы и позволяет независимо развивать отдельные части приложения.

                HTTP Request
                      │
                      ▼
             Transport Layer
          (Fiber, Handler, DTO)
                      │
                      ▼
              Use Case Layer
          (Business Scenarios)
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
   Domain Services         Repository Layer
                                  │
                                  ▼
                      PostgreSQL + PostGIS

### 6.1 Transport Layer

Транспортный слой отвечает за взаимодействие приложения с внешним миром.

В рамках проекта он реализован с использованием Fiber и включает:

- маршрутизацию HTTP-запросов;
- обработчики (Handlers);
- DTO;
- middleware;
- преобразование HTTP-запросов в вызовы бизнес-сценариев.

Транспортный слой не содержит бизнес-логики и не работает с базой данных напрямую.

### 6.2 Use Case Layer

Use Case представляет собой уровень бизнес-сценариев приложения.

Каждый use case реализует законченную пользовательскую операцию, координируя взаимодействие между доменной моделью, репозиториями и инфраструктурными сервисами.

Именно этот слой содержит основную бизнес-логику системы.

### 6.3 Domain Layer

Доменный слой содержит модели предметной области и доменные сервисы.

Он описывает основные сущности системы и правила их взаимодействия независимо от используемых технологий.

Domain не зависит от HTTP, PostgreSQL, Fiber, sqlx и других инфраструктурных компонентов.

### 6.4 Repository Layer

Repository является единственной точкой доступа к базе данных.

Он отвечает за выполнение SQL-запросов, преобразование данных между PostgreSQL и доменными моделями, а также инкапсулирует детали хранения информации.

Остальные слои приложения не взаимодействуют с базой данных напрямую.

### 6.5 Infrastructure Services

Инфраструктурные сервисы предоставляют вспомогательные возможности, необходимые для работы приложения.

К ним относятся:

- конфигурация приложения;
- логирование;
- работа с JWT;
- хеширование паролей;
- подключение к базе данных;
- другие технические компоненты.

Инфраструктурные сервисы не содержат бизнес-логики и используются другими слоями приложения при необходимости.

### 6.6 Layer Interaction Rules

Взаимодействие между слоями приложения подчиняется следующим правилам:

- Transport вызывает только Use Case.
- Use Case может обращаться к Domain, Repository и Infrastructure Services.
- Repository взаимодействует исключительно с PostgreSQL.
- Domain не зависит от инфраструктурных компонентов.
- Ни один слой не может нарушать направление зависимостей, определённое архитектурой проекта.

## 7. Project Structure

Структура проекта отражает архитектурные принципы, принятые при его проектировании.

Исходный код организован таким образом, чтобы физическая структура каталогов соответствовала логической структуре системы. Это упрощает навигацию по проекту, уменьшает связанность компонентов и облегчает дальнейшее развитие приложения.

Основные каталоги проекта представлены ниже.

backend/
├── cmd/
│   └── api/
├── configs/
├── docs/
│   ├── adr/
│   └── architecture.md
├── internal/
│   ├── app/
│   ├── config/
│   ├── domain/
│   ├── repository/
│   ├── service/
│   ├── transport/
│   └── usecase/
├── migrations/
├── pkg/
├── Dockerfile
├── docker-compose.yml
├── Makefile
└── go.mod

### cmd

Каталог содержит точки входа (entry points) приложения.

Каждое исполняемое приложение проекта располагается в отдельном подкаталоге.

В текущей реализации основной точкой входа является `cmd/api`, содержащий запуск HTTP-сервера.

### internal

Каталог `internal` содержит основную бизнес-логику приложения.

Именно здесь располагаются все архитектурные слои backend-системы: транспортный уровень, сценарии использования, доменная модель, репозитории и инфраструктурные компоненты.

Код внутри `internal` не предназначен для использования внешними приложениями.

### domain

Каталог содержит модели предметной области и доменные сервисы.

Доменный слой не зависит от технологий хранения данных, HTTP или инфраструктурных компонентов и описывает исключительно бизнес-модель системы.

### usecase

Каталог содержит сценарии использования приложения.

Каждый use case реализует законченную бизнес-операцию и координирует взаимодействие между остальными слоями системы.

### repository

Каталог содержит реализацию доступа к данным.

На текущем этапе используется реализация для PostgreSQL на основе sqlx.

### transport

Каталог содержит транспортные реализации приложения.

В настоящее время используется HTTP-транспорт на базе Fiber.

При необходимости архитектура допускает добавление других транспортов без изменения бизнес-логики.

### service

Каталог содержит сервисы предметной области, реализующие сложные вычисления и алгоритмы, которые не относятся к отдельным сущностям предметной области.

В проекте данный каталог используется преимущественно для реализации геометрических вычислений и алгоритмов автоматического раскроя.

### config

Каталог содержит механизм загрузки конфигурации приложения и описание структуры конфигурационных параметров.

### app

Каталог отвечает за сборку приложения как единой системы.

Здесь выполняется создание основных компонентов приложения, настройка зависимостей и подготовка инфраструктуры перед запуском сервера.

### pkg

Каталог содержит вспомогательные пакеты общего назначения, не относящиеся непосредственно к предметной области приложения.

Например:
- логирование;
- JWT;
- работа с паролями;
- общие ошибки.

### migrations

Каталог содержит SQL-миграции Goose, описывающие эволюцию структуры базы данных.

Каждое изменение схемы базы данных оформляется отдельной миграцией.

### docs

Каталог содержит архитектурную и техническую документацию проекта.

Ключевыми документами являются:
- Architecture;
- Architecture Decision Records (ADR);
- документация API.

## 8. Data Flow

Каждый пользовательский запрос проходит через несколько последовательных этапов обработки.

На каждом этапе выполняется строго определённый набор задач. Благодаря этому бизнес-логика, транспортный уровень, доступ к данным и инфраструктурные компоненты остаются независимыми друг от друга.

Типичный жизненный цикл HTTP-запроса представлен ниже.

                HTTP Request
                      │
                      ▼
                Fiber Router
                      │
                      ▼
                 HTTP Handler
                      │
            Parse & Validate DTO
                      │
                      ▼
                   Use Case
          ┌───────────┴────────────┐
          ▼                        ▼
   Domain Services         Repository
                                   │
                                   ▼
                        PostgreSQL + PostGIS
                                   │
                                   ▼
                           Repository
                                   │
                                   ▼
                               Use Case
                                   │
                         Response DTO
                                   │
                                   ▼
                             HTTP Response

### 8.1 Receiving Request

Запрос поступает на HTTP-сервер Fiber, который определяет маршрут обработки и передаёт управление соответствующему обработчику (Handler).

### 8.2 Transport Processing

Handler выполняет разбор HTTP-запроса, преобразует входные данные в DTO, выполняет базовую проверку корректности входных параметров и передаёт управление соответствующему сценарию использования.

На данном этапе не принимаются бизнес-решения.

### 8.3 Business Processing

Use Case реализует сценарий работы приложения.

При необходимости он обращается к доменным сервисам, репозиториям и инфраструктурным компонентам, координируя выполнение всей операции.

### 8.4 Data Access

Repository преобразует запросы бизнес-логики в SQL-запросы, взаимодействует с PostgreSQL/PostGIS и возвращает результаты обратно в Use Case.

Другие слои приложения не взаимодействуют с базой данных напрямую.

### 8.5 Response Generation

После завершения бизнес-сценария результат возвращается в Handler.

Handler преобразует данные в DTO ответа и формирует итоговый HTTP-ответ для клиента.

### Design Rule

Каждый слой приложения отвечает только за собственный этап обработки запроса.

Ни один компонент системы не должен пропускать архитектурные уровни или напрямую обращаться к компонентам, ответственность которых выходит за пределы его зоны ответственности.

## 9. Dependency Rules

Архитектура проекта определяет не только состав компонентов системы, но и правила их взаимодействия.

Для сохранения независимости архитектурных слоёв каждый компонент может взаимодействовать только с теми компонентами, которые определены архитектурой проекта.

Нарушение данных правил приводит к увеличению связанности компонентов, усложняет сопровождение системы и затрудняет её дальнейшее развитие.

                Transport
                     │
                     ▼
                 Use Case
              ┌────────────┐
              ▼            ▼
         Domain        Repository
                            │
                            ▼
                  PostgreSQL + PostGIS

Направление стрелки означает допустимое направление зависимости.

### 9.1 Transport Layer

Transport может зависеть только от:
- Use Case;
- DTO;
- middleware;
- инфраструктурных компонентов, необходимых для обработки HTTP.

Transport не должен:
- выполнять SQL-запросы;
- содержать бизнес-логику;
- обращаться к базе данных напрямую.

### 9.2 Use Case Layer

Use Case может использовать:
- Domain;
- Repository;
- Infrastructure Services.

Use Case не должен зависеть от Fiber, HTTP или других деталей транспортного уровня.

### 9.3 Domain Layer

Domain представляет собой наиболее независимую часть системы.

Доменные модели и доменные сервисы не должны зависеть от:
- Fiber;
- sqlx;
- PostgreSQL;
- JSON;
- HTTP;
- Docker;
- конфигурации приложения.

Domain описывает исключительно предметную область проекта.

### 9.4 Repository Layer

Repository является единственной частью приложения, взаимодействующей с PostgreSQL и PostGIS.

Repository не должен содержать бизнес-логику приложения.

Его задача — преобразование данных между базой данных и доменной моделью.

### 9.5 Infrastructure

Инфраструктурные компоненты предоставляют технические возможности приложения.

Они могут использоваться другими слоями системы, но не должны содержать бизнес-логику предметной области.

 Layer	         Can Depend On
Transport	    Use Case, Infrastructure
Use Case	    Domain, Repository, Infrastructure
Domain	        —
Repository	    Domain, PostgreSQL
Infrastructure	External Libraries

### Design Rule

При добавлении новых компонентов разработчик должен определить, к какому архитектурному слою относится данный компонент.

После этого компонент обязан соблюдать правила зависимостей, установленные для соответствующего слоя.

Если существующие правила оказываются недостаточными, изменение архитектуры должно быть оформлено отдельным Architecture Decision Record (ADR).

## 10. Configuration

Конфигурация приложения полностью отделена от исходного кода и рассматривается как часть внешнего окружения.

Все параметры запуска загружаются централизованно при инициализации приложения и после этого передаются в остальные компоненты системы в виде типизированной структуры.

Такой подход позволяет использовать один и тот же исполняемый файл в различных окружениях без изменения исходного кода.

             Environment Variables
                      │
                  .env / Docker
                      │
                      ▼
                 cleanenv.Load()
                      │
                      ▼
                  Config struct
                      │
          ┌───────────┴────────────┐
          ▼                        ▼
     HTTP Server              Database
          ▼                        ▼
       Logger                Other Services
    
### 10.1 Configuration Sources

Источником конфигурации являются переменные окружения.

Для локальной разработки используется файл `.env`.

В репозитории хранится файл `.env.example`, содержащий пример структуры конфигурации без секретных данных.

### 10.2 Configuration Loading

Загрузка конфигурации выполняется один раз при запуске приложения.

После успешной загрузки остальные компоненты системы работают только с объектом конфигурации и не обращаются напрямую к переменным окружения.

### 10.3 Configuration Principles

При работе с конфигурацией соблюдаются следующие правила:
- конфигурация загружается централизованно;
- параметры не дублируются в разных частях приложения;
- секретные данные не хранятся в репозитории;
- изменение конфигурации не требует изменения исходного кода.

## 11. Database Architecture

В качестве основной системы хранения данных используется PostgreSQL с расширением PostGIS.

PostgreSQL обеспечивает хранение данных приложения, а PostGIS расширяет возможности базы данных средствами пространственной обработки геометрических объектов.

Взаимодействие приложения с базой данных осуществляется исключительно через слой Repository.

            Backend
               │
         Repository Layer
               │
               ▼
      PostgreSQL + PostGIS
               │
     ┌─────────┴──────────┐
     ▼                    ▼
 Relational Data     Geometry Data

### 11.1 Data Storage

В базе данных хранятся:
- пользователи;
- проекты;
- поверхности;
- шаблоны;
- размещения;
- результаты вычислений;
- другие сущности предметной области.

### 11.2 Spatial Processing

Для выполнения стандартных пространственных операций используются встроенные возможности PostGIS.

Это позволяет эффективно выполнять проверки пересечений, вычисление площадей и другие геометрические операции без повторной реализации соответствующих алгоритмов средствами Go.

### 11.3 Database Evolution

Изменение структуры базы данных осуществляется исключительно посредством SQL-миграций Goose.

Каждое изменение схемы оформляется отдельной миграцией и становится частью истории проекта.

- документация поддерживается в актуальном состоянии одновременно с изменением исходного кода.

## 14. Architecture Decision Records

Все значимые архитектурные решения проекта документируются в виде Architecture Decision Records (ADR).

Каждый ADR фиксирует причины принятия решения, рассмотренные альтернативы и последствия выбора. Это позволяет сохранить историю развития архитектуры и облегчает понимание причин, по которым система устроена именно таким образом.

На текущем этапе проекта приняты следующие архитектурные решения:

- ADR-0001 — Layered Architecture;
- ADR-0002 — sqlx instead of ORM;
- ADR-0003 — Goose for Database Migrations;
- ADR-0004 — Environment-based Configuration;
- ADR-0005 — Docker-based Development Environment;
- ADR-0006 — Server-side Geometry Processing.

При появлении новых требований, влияющих на архитектуру системы, принимается новый ADR. Уже существующие ADR не переписываются, поскольку они отражают историю принятых архитектурных решений.
