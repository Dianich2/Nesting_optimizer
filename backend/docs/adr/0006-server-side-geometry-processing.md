# ADR-0006: Server-side Geometry Processing

## Status

Accepted

---

## Context

Проект Nesting Optimizer предназначен для создания, хранения, редактирования и автоматического размещения двумерных геометрических объектов.

В процессе работы пользователь взаимодействует с поверхностями, шаблонами и их размещением на рабочей области. Многие операции требуют выполнения геометрических вычислений, таких как проверка пересечений объектов, проверка выхода за границы поверхности, вычисление площадей, расстояний и выполнение алгоритмов автоматического раскроя.

На этапе проектирования необходимо определить, на каком уровне системы должна выполняться геометрическая обработка данных.

Существует несколько возможных вариантов: выполнение вычислений на стороне frontend, выполнение всей геометрии в backend либо разделение ответственности между backend и специализированными средствами PostgreSQL/PostGIS.

Выбранное решение оказывает влияние на архитектуру системы, распределение ответственности между компонентами, производительность приложения и возможность дальнейшего развития проекта.

---

## Requirements

Архитектура обработки геометрических данных должна:
- обеспечивать единый источник истины для результатов вычислений;
- исключать расхождение результатов между frontend и backend;
- эффективно использовать возможности PostGIS;
- позволять реализовывать сложные алгоритмы автоматического раскроя;
- обеспечивать возможность дальнейшего расширения геометрических возможностей системы;
- минимизировать дублирование логики между компонентами;
- сохранять чёткое разделение ответственности между frontend, backend и базой данных;
- сохранять отзывчивость интерфейса при интерактивном перемещении объектов.

## Decision

В проекте принято решение использовать гибридную модель обработки геометрических данных, при которой ответственность распределяется между frontend, backend и PostgreSQL/PostGIS в соответствии с назначением каждого компонента системы.

Frontend отвечает исключительно за взаимодействие с пользователем и визуализацию данных. Во время интерактивного редактирования объектов frontend может выполнять временные клиентские вычисления, необходимые для обеспечения плавности интерфейса и удобства работы пользователя. Результаты таких вычислений не считаются окончательными и не используются как источник истины.

Backend является единственным источником истины для всех бизнес-решений, связанных с геометрией. Именно backend принимает окончательное решение о корректности размещения объектов, возможности их сохранения, запуске алгоритмов автоматического раскроя и выполнении других бизнес-сценариев.

PostGIS используется для хранения геометрических данных и выполнения базовых пространственных операций, предоставляемых системой PostgreSQL. К таким операциям относятся проверка пересечений, вычисление площадей, проверка принадлежности объектов, пространственные запросы и другие стандартные геометрические функции.

Go отвечает за координацию сценариев работы приложения, взаимодействие между компонентами системы и реализацию сложных алгоритмов автоматического раскроя, которые выходят за рамки стандартных возможностей PostGIS.

Таким образом, каждая часть системы используется для решения тех задач, для которых она подходит наилучшим образом.

---

## Consequences

### Advantages

После принятия данного решения проект получает следующие преимущества:
- backend становится единственным источником истины для всех геометрических решений;
- отсутствует дублирование сложной бизнес-логики между frontend и backend;
- frontend сохраняет высокую отзывчивость интерфейса при интерактивной работе пользователя;
- возможности PostGIS используются по своему прямому назначению без повторной реализации пространственных операций;
- Go сосредотачивается на реализации бизнес-логики и алгоритмов автоматического раскроя;
- архитектура позволяет независимо развивать frontend, backend и геометрические алгоритмы;
- уменьшается вероятность расхождения результатов вычислений между различными компонентами системы;
- упрощается тестирование геометрической логики, поскольку окончательные вычисления выполняются на стороне backend.

### Trade-offs

При этом разработчики осознанно принимают следующие компромиссы:
- часть операций требует обращения к backend для получения окончательного результата;
- архитектура становится более сложной из-за разделения ответственности между несколькими компонентами;
- разработчикам необходимо понимать, какие геометрические операции должны выполняться в Go, а какие — средствами PostGIS;
- временные клиентские вычисления могут отличаться от окончательного результата, подтверждённого backend;
- реализация и тестирование системы требуют знания как алгоритмов вычислительной геометрии, так и возможностей PostGIS.

---

## Alternatives Considered

### Вся геометрия выполняется на frontend

Этот подход был отклонён, поскольку frontend не должен принимать окончательные бизнес-решения.

Кроме того, реализация сложной геометрической логики на стороне клиента привела бы к дублированию алгоритмов и увеличению вероятности расхождения результатов между клиентом и сервером.

### Вся геометрия выполняется средствами PostGIS

Данный подход также был рассмотрен.
PostGIS предоставляет большое количество встроенных пространственных функций и отлично подходит для выполнения стандартных геометрических операций.

Однако реализация сложных алгоритмов автоматического раскроя, эвристик и оптимизационных алгоритмов средствами SQL значительно усложнила бы разработку и сопровождение проекта.

### Вся геометрия выполняется в Go

Полный перенос всей геометрической обработки в Go также рассматривался.

Однако в этом случае потребовалось бы повторно реализовывать множество пространственных операций, уже присутствующих в PostGIS.

Такой подход увеличил бы объём кода, усложнил сопровождение системы и не позволил бы эффективно использовать возможности специализированной пространственной СУБД.

В результате была выбрана гибридная модель, использующая сильные стороны каждого компонента системы.

---

## Why This Decision Fits This Project

Проект Nesting Optimizer существенно отличается от большинства CRUD-приложений. Его ключевой особенностью является работа с двумерной геометрией и алгоритмами автоматического раскроя, которые требуют выполнения большого количества специализированных вычислений.

Использование гибридной модели позволяет эффективно распределить ответственность между компонентами системы.

Frontend обеспечивает удобство взаимодействия пользователя с системой и высокую отзывчивость интерфейса.

PostGIS используется для хранения геометрических объектов и выполнения стандартных пространственных операций, для которых он изначально предназначен.

Backend на Go координирует работу приложения, реализует бизнес-логику и выполняет сложные алгоритмы автоматического раскроя, которые невозможно или нецелесообразно реализовывать средствами SQL.

Такое распределение обязанностей позволяет использовать сильные стороны каждой технологии без дублирования функциональности и соответствует общей архитектурной концепции проекта, основанной на разделении ответственности между компонентами системы.
