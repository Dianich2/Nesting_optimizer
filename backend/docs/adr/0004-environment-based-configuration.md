# ADR-0004: environment-based configuration
## Status 
Accepted

---

## Context

Backend-приложение должно запускаться в разных окружениях: локально, в Docker, в тестовой среде и в будущем в production. В каждом окружении могут отличаться параметры запуска: порт HTTP-сервера, параметры подключения к базе данных, уровень логирования и другие настройки.

Если такие значения хранить непосредственно в коде, приложение становится жёстко привязанным к одному окружению. Любое изменение настроек потребует изменения исходного кода и повторной сборки приложения.

Кроме того, конфигурация может содержать чувствительные данные, например пароли, секреты JWT или параметры подключения к внешним сервисам. Такие значения не должны попадать в Git-репозиторий.

Поэтому приложению необходим единый механизм конфигурации, который позволяет изменять настройки без изменения исходного кода и поддерживает разные окружения.

---

## Requirements

Механизм конфигурации должен:
- позволять изменять настройки без изменения исходного кода;
- поддерживать разные окружения: local, test, production;
- не требовать пересборки приложения при изменении параметров;
- не хранить секретные значения в Git-репозитории;
- быть удобным для локальной разработки;
- хорошо работать с Docker Compose;
- предоставлять типобезопасную структуру конфигурации в Go-коде;
- позволять группировать настройки по смыслу.

---

## Decision

В проекте принято решение использовать конфигурацию на основе переменных окружения (Environment Variables).

Для локальной разработки используется файл `.env`, содержащий значения переменных окружения. В репозитории хранится файл `.env.example`, который описывает структуру конфигурации без хранения секретных данных.

Загрузка конфигурации в приложении осуществляется с помощью библиотеки **cleanenv**.

Конфигурация приложения представлена типизированной структурой `Config`, разделённой на логические группы:

- App;
- HTTP;
- Log;
- DB.

Каждая группа отвечает только за собственную область настроек приложения.

Для большинства параметров используются значения по умолчанию (`env-default`), что позволяет запускать приложение даже при отсутствии части переменных окружения.

Чтение конфигурации производится централизованно при запуске приложения. Остальная часть системы получает уже готовую структуру конфигурации и не обращается к переменным окружения напрямую.

---

## Consequences

### Advantages

После принятия данного решения проект получает следующие преимущества:
- конфигурация приложения полностью отделена от исходного кода;
- один и тот же бинарный файл может использоваться в разных окружениях без повторной сборки;
- секретные данные не хранятся в репозитории проекта;
- настройки приложения централизованы и загружаются через единый механизм;
- использование типизированной структуры Config уменьшает вероятность ошибок при работе с конфигурацией;
- разделение конфигурации на логические группы упрощает поддержку и дальнейшее развитие проекта;
- использование cleanenv сокращает объём шаблонного кода при загрузке конфигурации.

### Trade-offs

При этом разработчики осознанно принимают следующие компромиссы:
- необходимо поддерживать актуальность файлов `.env.example`;
- добавление новой настройки требует изменения структуры Config;
- некорректные или отсутствующие переменные окружения могут привести к невозможности запуска приложения;
- разработчики должны синхронизировать локальную конфигурацию с актуальной структурой проекта;
- часть ошибок конфигурации обнаруживается только при запуске приложения.

---

## Alternatives Considered

На этапе проектирования были рассмотрены различные способы хранения конфигурации приложения.

### Константы в исходном коде

Этот подход был отклонён, поскольку любое изменение параметров требовало бы изменения исходного кода и повторной сборки приложения. Кроме того, такой подход не позволяет удобно использовать разные окружения.

### Конфигурационные файлы (JSON/YAML)

Использование отдельных конфигурационных файлов также рассматривалось как возможный вариант.

Однако для backend-приложения, ориентированного на Docker и современные практики развёртывания, использование переменных окружения является более универсальным решением. Такой подход хорошо поддерживается контейнерными платформами и соответствует принципам **The Twelve-Factor App**, согласно которым конфигурация должна храниться во внешней среде (environment).

Использование специализированных библиотек для работы с конфигурацией также рассматривалось. Для данного проекта была выбрана библиотека cleanenv как простое и удобное решение, хорошо интегрирующееся с использованием переменных окружения.

---

## Why This Decision Fits This Project

Проект Nesting Optimizer изначально проектируется как масштабируемое backend-приложение, которое должно одинаково успешно работать в различных окружениях: локально, в Docker и в дальнейшем в production.

Использование конфигурации на основе переменных окружения позволяет полностью отделить настройки приложения от его исходного кода. Благодаря этому один и тот же скомпилированный бинарный файл может использоваться в различных окружениях без повторной сборки, а изменение параметров не требует внесения изменений в исходный код.

Централизованная загрузка конфигурации через библиотеку `cleanenv` и её представление в виде типизированной структуры `Config` обеспечивает единый механизм работы с настройками во всём приложении. Остальные компоненты системы получают уже готовую конфигурацию и не зависят от конкретного способа её загрузки.

Такой подход соответствует современной практике разработки backend-приложений, хорошо интегрируется с Docker Compose и поддерживает дальнейшее масштабирование проекта без изменения архитектурных принципов.

Данное решение согласуется с общей архитектурной концепцией проекта, основанной на разделении ответственности, независимости компонентов и возможности их дальнейшего развития без существенного влияния друг на друга.
