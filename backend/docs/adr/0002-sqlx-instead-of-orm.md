# ADR-0002: sqlx instead of orm

## Status
Accepted

---

## Context
Backend-приложение требует постоянного взаимодействия с базой данных PostgreSQL.

На этапе проектирования необходимо было выбрать технологию доступа к базе данных, которая должна обеспечивать удобство разработки, производительность, читаемость кода и возможность использования всех возможностей PostgreSQL.

Для языка Go существует несколько популярных подходов к работе с базой данных, среди которых можно выделить:
- database/sql;
- sqlx;
- GORM;
- Bun;
- Ent;
- SQLC.

Каждый из этих инструментов обладает собственными преимуществами и недостатками, поэтому выбор технологии должен основываться не на её популярности, а на требованиях конкретного проекта.

Проект Nesting Optimizer предполагает использование сложных SQL-запросов, работу с PostGIS, выполнение геометрических вычислений, использование транзакций и реализацию алгоритмов автоматического раскроя. Все эти особенности существенно влияют на выбор технологии доступа к данным.

---

## Requirements

Выбранная технология должна:
- обеспечивать полный контроль над SQL-запросами;
- поддерживать PostgreSQL и PostGIS без ограничений;
- упрощать работу с результатами запросов;
- не скрывать возможности СУБД за дополнительными абстракциями;
- хорошо подходить для реализации сложной бизнес-логики и алгоритмов.

---

## Decision
В качестве технологии доступа к базе данных принято решение использовать библиотеку **sqlx**, построенную поверх стандартного пакета **database/sql**.

Такое решение позволяет сохранить полный контроль над SQL-запросами, используя при этом более удобный API для работы с базой данных.

Библиотека sqlx предоставляет дополнительные абстракции над стандартным пакетом database/sql, значительно упрощающие работу с базой данных без потери контроля над SQL. Возможности, которые значительно упрощают разработку:

- автоматическое отображение результатов запросов в структуры Go;
- удобную работу с коллекциями данных;
- поддержку именованных параметров;
- дополнительные методы (`Get`, `Select`, `NamedExec`, `NamedQuery`, `In` и другие);
- полную совместимость со стандартным пакетом `database/sql`.

Использование sqlx особенно хорошо соответствует требованиям данного проекта, поскольку основная бизнес-логика предполагает выполнение сложных SQL-запросов, использование PostGIS, транзакций и геометрических операций.

Использование ORM было отклонено, поскольку проект требует полного контроля над SQL и активного использования возможностей PostgreSQL, которые удобнее реализовывать с помощью явных SQL-запросов.

---

## Consequences
### Advantages
После принятия данного решения проект получает следующие преимущества:
- разработчик сохраняет полный контроль над выполняемыми SQL-запросами;
- проект может использовать любые возможности PostgreSQL и PostGIS без ограничений;
- код остается максимально прозрачным для разработчиков, так как пишутся запросы на SQL напрямую;
- проще анализировать производительность;
### Trade-offs
При этом разработчики осознанно принимают следующие компромиссы:
- использование sqlx требует уверенного знания SQL и возможностей PostgreSQL;
- типовые операции CRUD необходимо реализовывать вручную;
- нет автоматической генерации связей между сущностями;
- необходимость следить за соответствием SQL и структур Go.

---

## Alternatives Considered
### database/sql

Стандартный пакет Go был рассмотрен в качестве возможного варианта.

Преимущества:
- входит в стандартную библиотеку;
- не требует дополнительных зависимостей;
- обеспечивает полный контроль над SQL;
- является основой для большинства других библиотек.

Причины отказа:

Несмотря на перечисленные преимущества, использование только database/sql приводит к большому количеству шаблонного кода. Разработчику приходится самостоятельно выполнять отображение результатов запросов в структуры, работать с Rows, Scan и реализовывать множество повторяющихся операций.

Для проекта с большим количеством сущностей это привело бы к увеличению объёма кода и снижению его читаемости.

### GORM

ORM GORM был рассмотрен как один из наиболее популярных инструментов работы с PostgreSQL в Go.

Преимущества:
- высокая скорость разработки CRUD-операций;
- автоматическое отображение структур;
- поддержка миграций и связей между сущностями;
- большое сообщество.

Причины отказа:

Проект ориентирован на выполнение большого количества сложных SQL-запросов, использование PostGIS и реализацию алгоритмов раскроя.

В подобных условиях разработчикам всё равно пришлось бы регулярно использовать Raw SQL, что уменьшило бы преимущества использования ORM и усложнило сопровождение проекта.

По этой причине было принято решение использовать инструмент, предоставляющий полный контроль над SQL.

---

## Why This Decision Fits This Project

Nesting Optimizer не является типичным CRUD-приложением. Значительная часть бизнес-логики связана с обработкой геометрических данных, использованием PostGIS, выполнением сложных SQL-запросов и реализацией алгоритмов автоматического раскроя.

В подобных условиях важнейшими требованиями становятся полный контроль над SQL, прозрачность выполняемых запросов и возможность использовать все возможности PostgreSQL без дополнительных ограничений.

Использование sqlx позволяет сохранить преимущества стандартного пакета database/sql, одновременно предоставляя более удобный API для работы с данными. Такой баланс между гибкостью, производительностью и удобством разработки делает sqlx наиболее подходящим выбором для данного проекта.

Использование sqlx позволяет сохранить баланс между удобством разработки, производительностью и полным контролем над уровнем доступа к данным, что соответствует архитектурным целям проекта.
