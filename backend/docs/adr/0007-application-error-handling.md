# ADR-0007: Application Error Handling

## Status

Accepted

---

## Context

Backend-приложение взаимодействует с клиентскими приложениями через HTTP API.

Во время обработки запросов могут возникать различные категории ошибок: ошибки валидации входных данных, нарушения бизнес-правил, конфликты уникальности, отсутствие требуемых сущностей, ошибки авторизации, а также внутренние ошибки инфраструктуры, связанные с базой данных или другими внешними компонентами.

Если каждый HTTP-обработчик будет самостоятельно определять формат ответа и соответствующий HTTP-статус, обработка ошибок станет неоднородной. Это приведёт к дублированию кода, усложнит сопровождение проекта и затруднит дальнейшее развитие API.

Кроме того, бизнес-логика приложения не должна зависеть от протокола HTTP. Use Case, Repository и Domain должны сообщать только о факте возникновения ошибки приложения, не зная, каким образом эта ошибка будет представлена клиенту.

Поэтому проекту необходим единый механизм представления ошибок приложения и отдельный механизм преобразования этих ошибок в HTTP-ответы.

---

## Requirements

Механизм обработки ошибок должен:

- обеспечивать единый формат ошибок во всём приложении;
- разделять ошибки приложения и их HTTP-представление;
- не допускать зависимости Domain, Repository и Use Case от HTTP-статусов и JSON-формата ответа;
- предоставлять удобные абстракции для создания и передачи ошибок между слоями;
- поддерживать подробные ошибки валидации с указанием конкретных полей;
- скрывать внутренние инфраструктурные ошибки от клиента;
- позволять HTTP-слою преобразовывать ошибки приложения в корректные HTTP-статусы и JSON-ответы.

---

## Decision

В проекте принято решение разделить ошибки приложения и способ их представления клиенту.

Для представления ошибок приложения используется собственный пакет `pkg/apperror`, содержащий тип `AppError`, который является единым представлением всех ошибок бизнес-логики и инфраструктуры.

Каждая ошибка приложения содержит:

- код ошибки (`Code`);
- человекочитаемое описание (`Message`);
- при необходимости — список ошибок отдельных полей (`Details`);
- внутреннюю ошибку (`Err`) для сохранения первоначальной причины возникновения ошибки.

Для упрощения создания ошибок используются специализированные функции-конструкторы (`Validation`, `Conflict`, `NotFound`, `Unauthorized`, `Forbidden`, `Internal`), а также вспомогательная функция `NewFieldError` для формирования ошибок отдельных полей.

Ошибки валидации могут содержать несколько ошибок одновременно, что позволяет вернуть пользователю полный список некорректных полей за один запрос.

Все Use Case возвращают только ошибки приложения (`AppError`) и не зависят от протокола HTTP или конкретного способа взаимодействия с клиентом.

Преобразование ошибок приложения в HTTP-ответы выполняется исключительно в транспортном слое. Для этого используется отдельный HTTP Error Handler, который сопоставляет коды ошибок приложения соответствующим HTTP-статусам и формирует единый JSON-ответ.

Внутренние ошибки инфраструктуры не передаются клиенту напрямую. Пользователь получает только безопасное сообщение об ошибке, тогда как первоначальная причина сохраняется внутри `AppError` и может использоваться для логирования и диагностики.

---

## Consequences

### Advantages

После принятия данного решения проект получает следующие преимущества:

- все ошибки приложения имеют единый формат представления;
- каждый слой приложения отвечает только за собственную область обработки ошибок;
- бизнес-логика полностью изолирована от HTTP и может использоваться независимо от транспортного слоя;
- уменьшается дублирование кода при обработке ошибок в HTTP-обработчиках;
- пользователи получают единообразные и понятные сообщения об ошибках;
- ошибки валидации могут содержать информацию сразу о нескольких некорректных полях;
- внутренние ошибки инфраструктуры не раскрываются клиенту;
- единый механизм обработки ошибок упрощает сопровождение, тестирование и дальнейшее развитие проекта.

### Trade-offs

При этом разработчики осознанно принимают следующие компромиссы:

- появляется дополнительный уровень абстракции между ошибками приложения и HTTP-ответами;
- необходимо поддерживать соответствие между кодами ошибок приложения и HTTP-статусами;
- при добавлении новой категории ошибок требуется обновить механизм преобразования ошибок в транспортном слое;
- проект использует собственную модель ошибок вместо стандартных ошибок Go, что требует соблюдения единых правил её использования;
- обработка ошибок становится более структурированной, но требует большего количества вспомогательного кода.

---

## Alternatives Considered

При проектировании механизма обработки ошибок были рассмотрены различные подходы.

### Использование только стандартных ошибок Go

Одним из возможных вариантов было использование только стандартного интерфейса `error` без введения собственной модели ошибок.

Преимущества такого подхода:

- отсутствует дополнительная инфраструктура;
- используется стандартный механизм языка Go;
- уменьшается количество собственного кода.

Причины отказа:

Стандартный интерфейс `error` не позволяет единообразно хранить код ошибки, дополнительные сведения о некорректных полях и внутреннюю причину возникновения ошибки. В результате логика преобразования ошибок в HTTP-ответы была бы распределена между различными обработчиками и содержала бы большое количество повторяющегося кода.

### Формирование HTTP-ответов непосредственно в Handler

Также рассматривался вариант, при котором каждый HTTP-обработчик самостоятельно определяет HTTP-статус и формирует JSON-ответ при возникновении ошибок.

Причины отказа:

Такой подход приводит к дублированию логики обработки ошибок, усложняет сопровождение проекта и делает поведение различных обработчиков менее единообразным. Кроме того, бизнес-логика начинает косвенно зависеть от особенностей транспортного слоя.

### Использование сторонних библиотек обработки ошибок

Использование специализированных библиотек также рассматривалось как возможный вариант.

Однако требования проекта не предполагают сложной иерархии исключений или специализированных механизмов обработки ошибок. Собственная реализация полностью покрывает потребности проекта, остаётся небольшой по объёму и легко адаптируется под дальнейшее развитие системы.

---

## Why This Decision Fits This Project

Nesting Optimizer представляет собой многослойное backend-приложение, построенное на принципах разделения ответственности. Каждый слой системы выполняет собственную задачу и не должен зависеть от деталей реализации других слоёв.

Использование собственной модели ошибок позволяет отделить бизнес-логику приложения от транспортного уровня. Use Case и Repository сообщают только о факте возникновения ошибки приложения, не принимая решений о том, каким HTTP-статусом или форматом ответа она должна быть представлена клиенту.

Единый механизм обработки ошибок обеспечивает одинаковое поведение всех HTTP-обработчиков, уменьшает количество повторяющегося кода и делает API предсказуемым для клиентских приложений.

Поддержка структурированных ошибок валидации позволяет возвращать пользователю информацию сразу обо всех некорректных полях, что повышает удобство использования API.

Данное решение соответствует общей архитектурной концепции проекта, основанной на разделении ответственности между слоями приложения, независимости компонентов и возможности их дальнейшего развития без изменения существующих архитектурных принципов.
