# ADR-0001: Layered architecture

## Status
Accepted

---

## Context
Бэкенд-приложение должно поддерживать пользователей, проекты, поверхности, шаблоны, размещения, геометрическую проверку и алгоритмы вложенности.

Если вся логика размещена непосредственно в обработчиках HTTP, код быстро становится сложным для понимания и сопровождения. Обработчики будут одновременно содержать парсинг HTTP, проверку, бизнес-правила, SQL-запросы, обработку ошибок и форматирование ответов.

Это создает ряд проблем:
- распределение обязанностей;
- тестирование бизнес-логики становится сложным;
- изменение одной технической детали может повлиять на множество несвязанных файлов;
- замена инфраструктуры, например, уровня базы данных, становится сложной;
- масштабирование проекта становится сложнее по мере добавления новых функций.

Проект также содержит нетривиальные рабочие процессы. Многие операции не являются простыми атомарными вызовами к базе данных. Например, создание размещения может потребовать геометрических проверок, проверок доступа, операций с базой данных и форматирования результатов.

Поэтому приложению необходимо четкое разделение между транспортом, бизнес-логикой, сущностями предметной области и сохранением данных.

---

## Decision
Использовать слоистую архитектуру для бэкенд-приложения.

Основные уровни:
- Доменный слой (Domain)
- Сценарии использования (Use Case)
- Репозиторий (Repository)
- HTTP-транспорт (Transport HTTP)
- Инфраструктурные сервисы (Infrastructure services)

Типичный поток обработки запроса:
HTTP-запрос
    ↓
Обработчик (Handler)
    ↓
Сценарий использования (Use Case)
    ↓
Репозиторий
    ↓
База данных / Внешняя инфраструктура

### Domain
Доменный слой содержит чистые бизнес-сущности и доменные концепции, описывает предметную область, а не способ хранения данных или взаимодействия по сети.

Доменный слой не должен зависеть от:
- Fiber;
- sqlx;
- PostgreSQL;
- JSON DTO;
- типов HTTP-запросов и ответов.

Доменные модели должны отражать концепции проекта независимо от деталей технической реализации.

### Use Case
Уровень вариантов использования содержит сценарии работы приложения.

Варианты использования координируют такие действия, как:
- создание пользователя;
- создание проекта;
- добавление шаблона;
- проверка размещения;
- запуск алгоритмов раскроя.

Варианты использования могут обращаться к репозиториям, доменным сервисам и сервисам инфраструктуры, но они не должны ничего знать о Fiber или деталях, специфичных для HTTP.

### Repository
Уровень репозиториев отвечает за доступ к базе данных.Repository является единственной частью приложения, которая знает, как именно данные хранятся в базе.

Репозитории могут:
- выполнять SQL-запросы;
- отображать строки базы данных на структуры Go;
- преобразовывать ошибки базы данных в ошибки приложения.

Репозитории не должны ничего знать об HTTP, Fiber, параметрах запроса или форматировании ответа.

### Transport HTTP
Транспортный уровень HTTP отвечает исключительно за взаимодействие с клиентами.

Обработчики могут:
- считывать HTTP-запросы;
- декодировать DTO;
- проверять формат запроса;
- вызывать сценарии использования (use cases);
- преобразовывать результаты выполнения сценариев в HTTP-ответы.

Обработчики не должны содержать SQL-запросы или сложную бизнес-логику.

## Consequences
### Advantages
- Четкое разделение зон ответственности.
- Бизнес-логику проще тестировать без использования HTTP.
- Реализацию репозитория можно изменить с минимальными правками в других слоях.
- HTTP-транспорт можно заменить или расширить без переписывания основной логики.
- Доменные сущности остаются независимыми от фреймворков и инфраструктуры.
- Проект легче масштабировать при добавлении новых модулей.
### Disadvantages
- Проект содержит больше файлов и пакетов.
- На начальном этапе разработка может казаться более медленной.
- Разработчикам необходимо строго соблюдать правила управления зависимостями.
- Для очень небольших приложений такая архитектура может показаться избыточной.

## Alternatives Considered
### Обработчик (handler) напрямую обращается к базе данных
От этого подхода отказались, так как он смешивает HTTP-логику, бизнес-правила и SQL-код в одном месте. Это решение подходит для очень маленьких приложений, но по мере роста проекта его становится сложно поддерживать.
### Обработчик напрямую обращается к репозиторию, минуя уровень сценариев использования (use cases)
Этот подход был отвергнут, поскольку многие операции в проекте представляют собой полноценные сценарии работы приложения, а не просто простые операции с базой данных. Уровень сценариев использования необходим для координации валидации, проверки прав доступа, работы с геометрией и операций сохранения данных.
### Структура в стиле MVC
Этот подход не был выбран, так как он может привести к рассредоточению бизнес-логики между контроллерами и моделями. Проект требует более строгого разделения между предметной областью (domain), сценариями использования, уровнем сохранения данных и транспортным уровнем.
